# قواعد صارمة: حماية الكود والبيانات (مشروع Hissaby Pro)

## 1. حماية الكود

1. لا تعدّل أي ملف أو دالة لم يُطلب تعديلها صراحة. نفّذ المطلوب فقط دون إعادة هيكلة أو تحسينات أو تنظيف جانبي.
2. لا تحذف ولا تعيد كتابة ملفات كاملة. استخدم تعديلات صغيرة ومحددة فقط (`replace_file_content`).
3. لا تغيّر أسماء الدوال أو الملفات أو المتغيرات أو واجهات الاستدعاء (APIs) الحالية.
4. لا تحدّث إصدارات المكتبات ولا تضف أو تحذف حزماً (dependencies) دون إذن مسبق.
5. لا تغيّر التصميم أو النصوص أو الترجمات أو الألوان أو أي جزء خارج نطاق المهمة المطلوبة.
6. قبل أي تعديل: اشرح باختصار ما ستغيّره وفي أي ملفات، وانتظر موافقة المستخدم إن كان التغيير يمس أكثر من ملفين أو منطق الأعمال.
7. اعمل نسخة احتياطية (Git commit أو نسخة من الملف) قبل أي تعديل، وأخبر المستخدم بكيفية التراجع عنه.
8. إن لم تفهم شيئاً أو وجدت خطأً في كود آخر، أبلغ المستخدم ولا تصلحه من تلقاء نفسك.

## 2. حماية البيانات

1. ممنوع منعاً باتاً حذف أو مسح أو إعادة إنشاء أي جدول أو قاعدة بيانات أو ملف بيانات (DROP, TRUNCATE, DELETE بدون شرط، أو حذف ملف .db أو مفاتيح localStorage).
2. أي تغيير في هيكل قاعدة البيانات يتم عبر Migration آمن يحفظ البيانات الحالية، ويُجرَّب أولاً على نسخة اختبار.
3. لا تنفذ أي أمر على البيانات الحقيقية. استخدم بيانات تجريبية للاختبار.
4. خذ نسخة احتياطية كاملة من قاعدة البيانات قبل أي Migration أو تعديل في طبقة البيانات أو المزامنة.
5. لا تغيّر منطق الحسابات المالية أو الأرصدة أو ترقيم الفواتير.
6. لا تعدّل مفاتيح Supabase أو ملفات الإعدادات (.env) ولا ترفع أي سر إلى أي مكان.
7. لا تشغّل أوامر خطرة في الطرفية (rm -rf, git reset --hard, git clean, git push --force, flutter clean مع حذف بيانات) دون إذن صريح من المستخدم.

## 3. طريقة العمل المتبعة دائماً

- اعمل خطوة صغيرة واحدة في كل مرة، ثم اختبرها قبل الانتقال للتالية.
- بعد كل تعديل، اذكر قائمة بالملفات التي غُيّرت فقط.
- إذا كانت المهمة قد تضر بالكود أو البيانات، توقف واسأل المستخدم أولاً.
- عند أي شك: لا تنفّذ، اسأل أولاً.
